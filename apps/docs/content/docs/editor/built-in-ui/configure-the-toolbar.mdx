Compare three ways to shape the built-in toolbar, then add the focused version to the `/sample.docx` project from the
[Quickstart](/editor/quickstart).

## Try the toolbar configurations

Expand the Editor and switch between the three configurations:

1. **Group** shows only the controls named in `groups`, placed in the left, center, and right regions.
2. **Remove** starts with the default toolbar and removes Bold and Italic with `excludeItems`.
3. **Add** keeps the grouped toolbar and appends an **Add note** action with `customButtons`. Place the caret in the
   document, then run it to insert `Review note: `.

## Choose a strategy

Use `groups` when your workflow needs a focused allowlist. Use `excludeItems` when the default toolbar already fits and
only a few controls should be removed. Use `customButtons` to add application actions that run through SuperDoc's command
context.

Keep the result predictable. Avoid combining a long `groups` allowlist with a long `excludeItems` list.

## Check the narrow layout

`responsiveToContainer: true` measures the toolbar mount instead of the browser window. When space runs out, controls
move into the overflow menu. SuperDoc adds the overflow trigger when a configured control moves there; `groups` only
needs to list the controls your application uses.

`excludeItems` applies to the full-width row, but the current runtime does not apply the exclusion after a control moves
into overflow. Use `groups` when a control must stay hidden at every supported width.

Resize the Editor to your narrowest supported width. Every required control should remain reachable, and the toolbar
should not add horizontal page overflow. See [Layout](/editor/built-in-ui/responsive-layout) for document scaling,
contained scrolling, and fullscreen behavior.

The toolbar reads state from the Editor. Controls become active or disabled as the selection, document mode, and current
content change.
